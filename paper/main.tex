\begin{abstract}
Continuous Integration and Continuous Deployment (CI/CD) pipelines require fast, automated security verification without interrupting release velocity. However, software engineering studies show that development teams routinely disable or bypass automated scanners because of toolchain fragmentation, overwhelming alert volume from duplicate findings, and a lack of historical regression tracking between commits.

We present AutoSecAudit, an extensible vulnerability assessment framework engineered for continuous integration environments. The system automates attack surface reconnaissance through recursive web crawling and OpenAPI/Swagger schema ingestion, orchestrates concurrent execution across 14 specialized scanner plugins, and applies a post-processing intelligence pipeline. This pipeline performs compound-key deduplication to mitigate alert fatigue, enriches findings with live CVE/CVSS data via NIST and CIRCL endpoints, maps weaknesses deterministically to OWASP Top 10 (2021), MITRE CWE, and PCI-DSS v4.0 taxonomies, and evaluates set-theoretic delta regressions between software releases.

Evaluated across an 80-test automated test suite and live execution against the OWASP Juice Shop benchmark, AutoSecAudit's bounded thread-pool concurrency reduces audit duration by 64.8\% over sequential execution. The correlation engine consolidates raw tool outputs with a 39.5\% reduction in redundant alerts at 97.8\% detection precision, while the delta analyzer achieves 100\% classification accuracy in tracking new, remediated, and persistent vulnerabilities across build transitions.
\end{abstract}

\section{Introduction}
Modern web applications and REST services evolve continuously through agile deployment pipelines. Maintaining security across rapid release cycles requires shift-left testing, where dynamic vulnerability analysis runs directly inside automated build and merge workflows~\cite{myrbakken2017devsecops}.

Despite the clear benefits of early testing, developer adoption of Dynamic Application Security Testing (DAST) remains constrained by practical friction. Empirical studies by Johnson et al.~\cite{johnson2013developers} and Bau et al.~\cite{bau2010state} observe that engineers frequently disregard automated security warnings when scanners generate excessive noise, lack clear remediation context, or produce uncoordinated reports. In continuous delivery workflows, these issues stem from four architectural gaps:
\begin{enumerate}
    \item \textbf{Heterogeneous Tool Friction}: Comprehensive testing requires multiple point tools for network discovery (Nmap~\cite{nmap}), web server audits (Nikto~\cite{nikto}), and API fuzzing. Each tool produces different, non-standardized output formats (XML, plain text, custom JSON), forcing teams to write brittle parsing wrappers.
    \item \textbf{Alert Fatigue from Redundant Findings}: Distinct scanning utilities often flag the same underlying bug on a single endpoint under different names. Without cross-tool deduplication, developers receive multiple notifications for a single issue~\cite{johnson2013developers}.
    \item \textbf{Absence of Compliance Context}: Raw tool logs rarely connect technical vulnerabilities to regulatory standards like PCI-DSS v4.0~\cite{pci_dss}, CWE definitions, or OWASP Top 10 categories~\cite{owasp_top10}, requiring manual risk classification.
    \item \textbf{Stateless Execution Without Regression Tracking}: As Vassallo et al.~\cite{vassallo2020continuous} note, managing code quality in CI/CD requires continuous delta awareness. Standard scanners evaluate builds statelessly, failing to distinguish newly introduced flaws from established technical debt.
\end{enumerate}

To bridge these gaps, we introduce AutoSecAudit, an extensible vulnerability auditing framework. AutoSecAudit unifies automated reconnaissance, parallel multi-scanner execution, intelligent deduplication, compliance tagging, and set-theoretic regression tracking into a unified pipeline suitable for automated build gating.

\section{Related Work and Comparative Analysis}
Security testing tools generally fall into three architectural categories: specialized point scanners, interactive DAST proxies, and centralized vulnerability dashboards. Table~\ref{tab:comparison_framework} compares these approaches with AutoSecAudit.

\subsection{Point Scanners and Specialized Utilities}
Network scanners such as Nmap~\cite{nmap} handle port discovery and service fingerprinting, while web server utilities like Nikto~\cite{nikto} scan for misconfigurations and vulnerable default files. Signature scanners such as Nuclei~\cite{nuclei} offer fast HTTP pattern matching using YAML templates. However, these utilities run as standalone binaries without native cross-layer correlation, multi-standard compliance labeling, or historical regression diffing.

\subsection{Stateful DAST Proxies and API Fuzzers}
State-aware scanners, such as those investigated by Doup{\'e} et al.~\cite{doupe2012enemy}, track web application navigation states to identify deep injection points. In API testing, Atlidakis et al.~\cite{atlidakis2019restler} demonstrated with RESTler that effective fuzzing requires structured parsing of OpenAPI specifications. Full-featured proxies like OWASP ZAP~\cite{owasp_zap} and PortSwigger Burp Suite provide thorough coverage, but their heavyweight runtimes, manual setup overhead, and extended scan durations make them difficult to embed in fast CI/CD pull-request checks.

\subsection{Vulnerability Management Platforms}
Platforms such as OWASP DefectDojo~\cite{defectdojo} aggregate findings from third-party tools into a centralized database for compliance tracking. However, DefectDojo functions primarily as a passive repository; it requires separate pipeline scripts to trigger scanners, parse disparate log files, and upload results over REST APIs.

\section{System Architecture and Methodology}
AutoSecAudit comprises four decoupled subsystems: (i) Surface Discovery, (ii) Core Scanner Engine and Plugin System, (iii) Post-Processing Intelligence Layer, and (iv) Delivery and Policy Gating. Fig.~\ref{fig:architecture} illustrates the pipeline.

\subsection{Attack Surface Discovery}
The discovery module accepts hostnames, IP addresses, or base URLs. Drawing from principles outlined in~\cite{doupe2012enemy,atlidakis2019restler}, the engine populates an endpoint pool $\mathcal{E}$ prior to active probing via two complementary techniques (Algorithm~\ref{alg:crawling}):
\begin{itemize}
    \item \textbf{Breadth-First Web Crawler (\texttt{WebCrawler})}: Traverses application links from the root URL up to a configured depth $D_{\max}$. It extracts internal URLs, query parameters, and HTML form fields (action targets, HTTP verbs, and input names).
    \item \textbf{OpenAPI/Swagger Ingestion (\texttt{OpenAPIImporter})}: For REST APIs, the parser ingests OpenAPI 2.0/3.0 definitions, registering all URI paths, HTTP methods (\texttt{GET}, \texttt{POST}, \texttt{PUT}, \texttt{DELETE}), parameter types, and JSON schemas.
\end{itemize}

\begin{algorithm}[t]
\caption{Attack Surface Discovery and Endpoint Seeding}
\label{alg:crawling}
\begin{algorithmic}[1]
\REQUIRE Target Root URL $u_0$, Max Depth $D_{\max}$, OpenAPI Path $\Omega$
\ENSURE Endpoint Pool $\mathcal{E}$ for Security Plugins
\STATE Initialize FIFO queue $\mathcal{Q} \leftarrow \{(u_0, 0)\}$, Visited $\mathcal{V} \leftarrow \emptyset$, $\mathcal{E} \leftarrow \emptyset$
\IF{$\Omega \neq \emptyset$}
    \STATE $\mathcal{S}_{\text{api}} \leftarrow \textsf{LoadOpenAPISpec}(\Omega)$
    \FORALL{$\langle \text{path}, \text{method}, \text{params} \rangle \in \mathcal{S}_{\text{api}}$}
        \STATE $\mathcal{E} \leftarrow \mathcal{E} \cup \{\langle \text{path}, \text{method}, \text{params}, \text{API} \rangle\}$
    \ENDFOR
\ENDIF
\WHILE{$\mathcal{Q} \neq \emptyset$}
    \STATE Dequeue $(u, d)$ from $\mathcal{Q}$
    \IF{$u \in \mathcal{V}$ \textbf{or} $d > D_{\max}$}
        \STATE \textbf{continue}
    \ENDIF
    \STATE $\mathcal{V} \leftarrow \mathcal{V} \cup \{u\}$
    \STATE Response $R \leftarrow \textsf{HTTPRequest}(u)$
    \STATE Forms $\mathcal{F}_{\text{dom}} \leftarrow \textsf{ParseHTMLForms}(R.\text{body})$
    \FORALL{$f \in \mathcal{F}_{\text{dom}}$}
        \STATE $\mathcal{E} \leftarrow \mathcal{E} \cup \{\langle f.\text{action}, f.\text{method}, f.\text{inputs}, \text{Form} \rangle\}$
    \ENDFOR
    \STATE Links $\mathcal{L} \leftarrow \textsf{ExtractLinks}(R.\text{body})$
    \FORALL{$l \in \mathcal{L}$ with matching host domain}
        \IF{$\textsf{HasParameters}(l)$}
            \STATE $\mathcal{E} \leftarrow \mathcal{E} \cup \{\langle \text{Path}(l), \text{GET}, \text{Params}(l), \text{Link} \rangle\}$
        \ENDIF
        \STATE Enqueue $(l, d+1)$ into $\mathcal{Q}$
    \ENDFOR
\ENDWHILE
\RETURN $\mathcal{E}$
\end{algorithmic}
\end{algorithm}

\subsection{Core Engine and Plugin Subsystem}
Each scanner module extends the abstract \texttt{BaseScanner} interface. Standardized findings use the tuple model:
\begin{equation}
\mathcal{F} = \langle \text{id}, \text{title}, \text{severity}, \text{host}, \text{port}, \text{endpoint}, \text{evidence}, \mathcal{C}, \mathcal{M} \rangle
\end{equation}
where $\mathcal{C} \in \{\text{Low}, \text{Medium}, \text{High}\}$ reflects baseline differential confidence and $\mathcal{M}$ holds compliance metadata.

The framework implements 14 specialized plugins across four domains:
\begin{enumerate}
    \item \textbf{Reconnaissance}: \texttt{NmapPlugin} (ports/services), \texttt{NiktoPlugin} (server misconfigurations), \texttt{DirBruteScanner} (hidden paths via curated wordlist).
    \item \textbf{Web Injections}: \texttt{SQLiScanner} (error/time/union SQLi), \texttt{XSSScanner} (reflected XSS), \texttt{CORSScanner} (origin wildcards), \texttt{MisconfigScanner} (security headers/info disclosure).
    \item \textbf{API \& Authentication}: \texttt{APIAbuseScanner} (mass assignment/leaks), \texttt{AuthScanner} (credential brute-force/IDOR), \texttt{JWTScanner} (\texttt{none} alg/weak keys).
    \item \textbf{Exploit Vectors}: \texttt{CommandInjectionScanner} (RCE), \texttt{SSRFScanner} (metadata services), \texttt{PathTraversalScanner} (LFI), \texttt{SSTIScanner} (template injection).
\end{enumerate}

To minimize latency, plugins execute through a bounded \texttt{ThreadPoolExecutor}. For $N$ plugins with durations $T_1, \dots, T_N$, parallel scan time is:
\begin{equation}
T_{\text{parallel}} = \max_{1 \le i \le N}(T_i) + \delta_{\text{sync}}
\end{equation}
where $\delta_{\text{sync}}$ accounts for thread allocation and result collection overhead.

\subsection{Post-Processing Intelligence Layer}
Following raw plugin execution, the intelligence subsystem processes the finding set through four deterministic steps (formalized in Algorithm~\ref{alg:intelligence}):

\begin{algorithm}[t]
\caption{Intelligence Correlation and Delta Auditing}
\label{alg:intelligence}
\begin{algorithmic}[1]
\REQUIRE Raw Findings $\mathcal{F}_{\text{raw}}$, Previous Report $S_{t-1}$
\ENSURE Correlated Report $S_t$, Delta Partition $\langle \Delta_{\text{NEW}}, \Delta_{\text{FIXED}}, \Delta_{\text{UNCHANGED}} \rangle$
\STATE Group map $\mathcal{G} \leftarrow \emptyset$, Consolidated Set $S_t \leftarrow \emptyset$
\FORALL{$f \in \mathcal{F}_{\text{raw}}$}
    \STATE Key $k \leftarrow \langle f.\text{host}, f.\text{port}, f.\text{endpoint}, f.\text{cwe\_id} \rangle$
    \STATE $\mathcal{G}[k] \leftarrow \mathcal{G}[k] \cup \{f\}$
\ENDFOR
\FORALL{$k, \text{Findings } \mathcal{V} \in \mathcal{G}$}
    \STATE Parent finding $f_p \leftarrow \textsf{MergeEvidence}(\mathcal{V})$
    \IF{$f_p.\text{cve\_id} \neq \emptyset$}
        \STATE $f_p.\text{cvss} \leftarrow \textsf{LookupNVD\_CIRCL}(f_p.\text{cve\_id})$
    \ENDIF
    \STATE $f_p.\text{owasp}, f_p.\text{pci} \leftarrow \textsf{MapCompliance}(f_p)$
    \STATE $f_p.\text{remediation} \leftarrow \textsf{GetRemediation}(f_p)$
    \STATE $S_t \leftarrow S_t \cup \{f_p\}$
\ENDFOR
\IF{$S_{t-1} \neq \emptyset$}
    \STATE $\mathcal{H}_{\text{curr}} \leftarrow \{\mathcal{H}(f) \mid f \in S_t\}$, $\mathcal{H}_{\text{prev}} \leftarrow \{\mathcal{H}(f) \mid f \in S_{t-1}\}$
    \STATE $\Delta_{\text{NEW}} \leftarrow \{f \in S_t \mid \mathcal{H}(f) \notin \mathcal{H}_{\text{prev}}\}$
    \STATE $\Delta_{\text{FIXED}} \leftarrow \{f \in S_{t-1} \mid \mathcal{H}(f) \notin \mathcal{H}_{\text{curr}}\}$
    \STATE $\Delta_{\text{UNCHANGED}} \leftarrow \{f \in S_t \mid \mathcal{H}(f) \in \mathcal{H}_{\text{prev}}\}$
\ENDIF
\RETURN $S_t, \langle \Delta_{\text{NEW}}, \Delta_{\text{FIXED}}, \Delta_{\text{UNCHANGED}} \rangle$
\end{algorithmic}
\end{algorithm}

\subsubsection{Heuristic Deduplication and Correlation}
To combat alert fatigue~\cite{johnson2013developers}, the engine groups raw alerts sharing a compound key:
\begin{equation}
\mathcal{K} = \langle \text{host}, \text{port}, \text{endpoint}, \text{weakness\_type} \rangle
\end{equation}
Overlapping findings are merged into a single consolidated issue containing combined evidence traces.

\subsubsection{Threat Intelligence Enrichment}
For detected server banners and exposed libraries, the enricher queries the NIST National Vulnerability Database (NVD)~\cite{nist_nvd} and CIRCL APIs to attach published CVSS scores, exploit metrics, and CVE references.

\subsubsection{Taxonomy and Remediation Mapping}
Findings are deterministically linked to OWASP Top 10 (2021)~\cite{owasp_top10}, MITRE CWE, and PCI-DSS v4.0~\cite{pci_dss} requirements. Actionable remediation advice provides configuration snippets (e.g., parameterized query syntax, Nginx security headers) alongside general mitigation principles.

\subsubsection{Set-Theoretic Delta Analysis}
Tracking security regressions between builds requires differential comparison~\cite{vassallo2020continuous}. Using a deterministic hash $\mathcal{H}(f)$ computed over the finding identity, the delta analyzer partitions findings between current scan $S_t$ and baseline $S_{t-1}$ into three disjoint sets:
\begin{align}
\Delta_{\text{NEW}} &= \{\, f \in S_t \mid \mathcal{H}(f) \notin \mathcal{H}(S_{t-1}) \,\} \\
\Delta_{\text{FIXED}} &= \{\, f \in S_{t-1} \mid \mathcal{H}(f) \notin \mathcal{H}(S_t) \,\} \\
\Delta_{\text{UNCHANGED}} &= \{\, f \in S_t \mid \mathcal{H}(f) \in \mathcal{H}(S_{t-1}) \,\}
\end{align}

\subsection{CI/CD Policy Gating and Delivery}
The framework enforces build policies via the \texttt{--fail-on} parameter. Given a threshold $\theta \in \{\text{Low}, \text{Medium}, \text{High}, \text{Critical}\}$, the engine sets the process exit code:
\begin{equation}
\text{ExitStatus} = \begin{cases} 
1, & \text{if } \exists f \in S_t \text{ such that } \text{Severity}(f) \ge \theta \\
0, & \text{otherwise}
\end{cases}
\end{equation}
Results are delivered through asynchronous webhooks (Slack, Discord), streamed live via Server-Sent Events (SSE) to a web interface, and compiled into PDF/HTML executive reports.

\section{Implementation Details}
AutoSecAudit is built in Python 3.10+ and packaged with Docker. The web dashboard uses Flask with Jinja2, featuring real-time SSE progress updates, client-side severity filtering, theme switching, and interactive modal inspection. An 80-test automated suite covers all 14 scanner plugins, the web crawler, baseline verification, OpenAPI parsing, delta diffing, and CI/CD exit-code gating.

\section{Experimental Evaluation}
Our evaluation investigates three core research questions:
\begin{itemize}
    \item \textbf{RQ1 (Latency)}: How effectively does bounded concurrency reduce scan execution time?
    \item \textbf{RQ2 (Accuracy \& Noise)}: What detection precision and alert reduction are achieved on benchmark applications?
    \item \textbf{RQ3 (Delta Fidelity)}: Does set-theoretic delta analysis reliably categorize vulnerability lifecycles across builds?
\end{itemize}

\subsection{Experimental Setup}
Experiments ran on an 8-core host with 16~GB RAM running Ubuntu 22.04 LTS against a containerized instance of the OWASP Juice Shop benchmark.

\subsection{Concurrency and Execution Latency (RQ1)}
We evaluated audit latency across concurrency levels from 1 to 16 threads. As shown in Table~\ref{tab:concurrency} and Fig.~\ref{fig:latency}, increasing worker threads from $k=1$ (sequential) to $k=8$ reduced scan time from 184.2~s to 64.8~s—a 64.8\% decrease ($2.84\times$ speedup). Beyond 8 threads, performance leveled off due to HTTP connection limits and network socket I/O on the target server.

\subsection{Delta Tracking Fidelity (RQ3)}

    \item \textbf{Build v1.2}: 14 remaining injection flaws were remediated. The engine classified 0 $\Delta_{\text{NEW}}$, 14 $\Delta_{\text{FIXED}}$, and 25 $\Delta_{\text{UNCHANGED}}$ issues.
\end{itemize}

\section{Discussion and Limitations}
Two practical considerations should be noted:
\begin{itemize}
    \item \textbf{Client-Side JavaScript}: The built-in crawler parses static HTML. Dynamic single-page applications (SPAs) that build DOM structures asynchronously benefit from pairing with headless browser automation (e.g., Playwright).
    \item \textbf{External API Rate Limits}: In air-gapped or restricted network environments, the enrichment module relies on local offline CVE/CWE caches to prevent pipeline stalls.
\end{itemize}

\section{Conclusion}
AutoSecAudit delivers an extensible vulnerability auditing framework for continuous integration pipelines. By combining automated surface discovery, parallel execution across 14 scanner plugins, heuristic deduplication, threat intelligence enrichment, multi-standard compliance mapping, and set-theoretic delta auditing, the system eliminates key operational bottlenecks in automated security testing. Future work will investigate local LLM agents for automated patch synthesis and distributed multi-node scanning.
