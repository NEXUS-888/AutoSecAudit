## Required changes
1. [AUD-08] `mcp_server.py:handle_verify_fix` lines 384–388: the code filters `engine.plugins` and then calls `engine.run()`. `run()` calls `load_plugins()` again, which rebuilds the full plugin list and undoes the filter. This fails the Required fix "Run only the plugins relevant to `vulnerability_type`". **Expected:** filter after `load_plugins()`, then call the stable API directly so nothing reloads, e.g. `engine.set_target(target, check_reachable=not mock_mode)` → `engine.run_plugins()` → `engine.generate_report()`. A `False` from `set_target` must return `ERROR`. (Alternatively, give `Engine.run` an optional plugin allowlist that it applies after loading.) **Checked next round by:** a new test that spies on `Engine.run_plugins` without patching `Engine.run`, calls `handle_verify_fix({"target":"http://localhost:8080","vulnerability_type":"sqli","mock":True})`, and asserts that the only plugin class in `engine.plugins` at run time is `SQLiScanner`.
2. [AUD-08] `mcp_server.py:handle_verify_fix` lines 401–421: if the relevant plugin errors, `Engine.run_plugins` records a `ScanResult` with `status` `"failed"`/`"timeout"`/`"skipped"` and no findings (`core/engine.py:232-260`). The handler then returns `RESOLVED` with `verified: true`. This breaks the rule "If the scan errors … return `status: "ERROR"` with `verified: false` — never `RESOLVED`". **Expected:** if any scan result from a relevant plugin has a status other than success, or if no relevant plugin ran at all, return `status: "ERROR"` with `verified: False`. **Checked next round by:** a test where a stubbed `SQLiScanner.run` raises (or its result has `status: "failed"`), asserting `status == "ERROR"` and `verified is False`.
3. [AUD-08] `mcp_server.py:handle_verify_fix` lines 384–386: an unmapped `vulnerability_type` (e.g. `"foo"`) gives an empty plugin list, so no filter is applied, and `target_tools={"foo"}` matches nothing. The result is `RESOLVED`/`verified: true`. An empty string matches every finding instead. **Expected:** if `vuln_type not in VULN_TYPE_TO_PLUGINS`, return `status: "ERROR"` with `verified: False` before any scan runs. Also add the newly mapped types to the tool's `enum` (`mcp_server.py:127`) or remove them from the map. **Checked next round by:** a test with `vulnerability_type="foo"` asserting `status == "ERROR"` and `verified is False`.

## Notes
- The deviation in `test_mcp_server.py:104` (`verified` now expected `False`/`ERROR`) is justified, but the test only passes if nothing is listening on `localhost:3000`. Consider pointing it at a closed high port, as `test_aud_08_verify_fix_unreachable_target` does.
- The `report_id` check uses `re.match` with `^…$`, which accepts a trailing `\n`, and it raises `TypeError` for a non-string ID. `re.fullmatch(r"[\w-]+", str(report_id))` is stricter. Not exploitable as written, because the candidate file can't exist.
- Matching by tool name uses substring checks against the plugins' actual `tool_name` values (e.g. `sqli_scanner`, `CORSScanner`, `DirBrute`). This works for the five enum types, and over-matching errs toward `STILL_VULNERABLE`, which is the safe direction.
