## Required changes
1. [AUD-19] ui/app.py `scan_async` / `BoundedScanExecutor` — the capacity check and the slot reservation are separate critical sections, so N concurrent requests with cap=1 can all get 200. → Reserve the slot atomically. Either run the check and insert the `scan_jobs[scan_id]` entry (status `"starting"`) in one `with scan_jobs_lock:` block, or use `threading.BoundedSemaphore(cap).acquire(blocking=False)` → 429 on failure, released in `_run_scan_background`'s `finally` (and on any early-return error path in `scan_async`). Release the reservation if setup fails after the reservation is made. ## Notes
- When cleanup marks a stuck job `error`, its worker thread keeps running and `active_count()` stops counting it. Zombie scans can therefore run beyond the cap, and the worker may later overwrite `status` and emit events after the `error` event. Consider having the worker check for an `error`/cancelled flag between stages and stop emitting.
- `progress_queue` is still created and filled through `put_nowait` (ui/app.py:238, 2786) but is only read by the legacy fallback path. It is an unbounded, write-only buffer on every job and should be removed.
- I couldn't run probe scripts because Bash execution is denied in this session. Both races above come from reading the code (lock scopes and statement order), not from a reproduction.
