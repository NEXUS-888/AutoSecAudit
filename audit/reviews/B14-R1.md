## Required changes
1. [AUD-37] `intelligence/recipes.py:get_fix_recipes`: the substring checks (`"header" in title`, `"redirect" in title`, `"secret" in title`, `"frame" in title`, …) run even when `recipe_key` was resolved from `vuln_type`. Example: `vuln_type="open_redirect"` with title "Open Redirect via Location header" gets the security-headers recipe, because branch 3 runs before branch 6. Expected: when `get_taxonomy(vuln_type)` resolves, choose the branch from `recipe_key` only. Title keywords may be used only when `vuln_type` is missing, and then only through word-boundary regexes (the `infer_taxonomy_from_text` result). (Checked next round by: a new test where `get_fix_recipes({"vuln_type":"open_redirect","title":"Open Redirect via Location header"})["nodejs"]` contains the redirect allowlist recipe (`safeRedirect`), not helmet.)
2. [AUD-37] `intelligence/remediation.py:get_remediation`: `remediation_key` is never actually used. Keys like `sqli_scanner:sqli` don't exist, and `TOOL_REMEDIATIONS` keys look like `sqli_scanner:login_bypass`. As a result, free-text `Type:` parsing (`_extract_finding_type`) still decides the tool-specific advice even when `vuln_type` is set. Expected: `remediation_key` resolves to real advice, for example through a key-indexed remediation dict or a defined mapping to `TOOL_REMEDIATIONS`. If `Type:` parsing is kept as a sub-type refinement, justify it under Deviations, and it must never pick advice for a different vuln family than `vuln_type`. (Checked next round by: a test with `vuln_type="sqli"`, a matching `tool_name`, and no `Type:` line, which gets advice via `remediation_key`. The verifier will also confirm `remediation_key` is referenced in a lookup that can succeed.)
3. [AUD-37] `intelligence/taxonomy.py` FALLBACK_RULES rule 12 and the customer-data regex in `danger_engine.py:classify_threat_category`: `\b(\.env|\.git…)` needs a word character right before the dot, so "Exposed .git directory" and "Exposed .env file" never match. Expected: use `(?<![\w.])\.(env|git)\b` or an equivalent. (Checked next round by: `infer_taxonomy_from_text("Exposed .env file").vuln_type == "secret_exposure"`.)
4. [AUD-38] `intelligence/danger_engine.py:calculate_security_posture` dedup loop: when two findings share a fingerprint, keep the one with the highest confidence weight (and highest severity), not the first one seen. (Checked next round by: a test with `[{fp:"x",sev:"Critical",conf:"low"},{fp:"x",sev:"Critical",conf:"high"}]` giving grade `F`, in both input orders.)

## Notes
- `test_compliance_mapper_never_overwrites_plugin_owasp_tag` can't catch an overwrite, because the plugin tag (A03) equals the taxonomy value for `vuln_type="sqli"`. Add a case where the plugin tag disagrees with the table, e.g. `vuln_type="auth"` with `owasp_tag="A03:2021"`.
- Fallback regexes run over `tool_name`, and `\bsqli\b` and `\bauth\b` don't match `sqli_scanner` or `auth_scanner` because `_` counts as a word character. Findings without a `vuln_type` lose the CWE they used to infer from the tool name.
- Findings without a fingerprint fall back to deduping on `tool:title`. That can merge distinct endpoints that share a title. It's low risk, since every `Finding.to_dict()` includes a fingerprint.
