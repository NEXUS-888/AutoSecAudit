## Required changes
1. [AUD-15] `ui/app.py:login` (lines 2296–2311), together with `_is_login_throttled` and `_record_login_failure`. This is a check-then-act race. `app.run` uses a threaded Werkzeug server by default, so N parallel bad logins from one IP all pass `_is_login_throttled` while `verify_user` is still hashing. None of them have recorded a failure yet, so an attacker gets an unlimited burst of guesses in every 5-minute window. That breaks "at most 5 failures per IP per 5 minutes".
   → Check and record in one critical section. For example, `_reserve_login_attempt(ip) -> bool`: under a single `LOGIN_FAILURES_LOCK` acquisition it prunes old entries, returns `False` if `len(recent) >= MAX_LOGIN_FAILURES`, and otherwise appends `now` and returns `True`. Call it before `verify_user` and return 429 when it returns `False`. On success, call `_clear_login_failures(ip)`, or remove that request's reserved timestamp.
   (Checked next round by: a new test that patches `auth.verify_user` to sleep ~0.2 s and return a failure. It starts 15 threads behind a `threading.Barrier`, each with its own `app.test_client()`, all posting bad logins with the same `REMOTE_ADDR`. It must assert that at most 5 responses are 401 and the rest are 429. The existing sequential 6th-attempt test must still pass.)

## Notes
- `config.py:49-52`: `os.chmod(…, 0o600)` runs after `write_text`, so on POSIX the key is briefly readable by everyone under the default umask. A chmod failure is also silently ignored, although the handoff says it logs a warning. Creating the file with `os.open(path, O_WRONLY|O_CREAT|O_EXCL, 0o600)` would fix both, and the `O_EXCL` flag also stops two first-start processes from writing different keys.
- `LOGIN_FAILURES` (`ui/app.py`) only removes an IP's entry when that IP logs in again, so the dict can keep growing with distinct source IPs. Consider pruning it occasionally.
- Shell execution was denied this session, so I couldn't run the concurrency probe. The race finding comes from reading the code. It follows directly from the two separate lock acquisitions with `verify_user` between them.
