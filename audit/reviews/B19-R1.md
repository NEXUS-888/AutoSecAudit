## Required changes
1. [AUD-64] `core/http_client.py:_execute_with_redirects` (`session.send(...)` at ~621 and ~657): the per-request wall-time limit starts only after the response headers arrive.
   - **Why:** `send(stream=True)` blocks until all headers are in. `hop_timeout` is a per-`recv` socket timeout, so it resets every time a byte arrives. A target that drips its status line and headers at 10 B/s keeps the request (and its plugin thread) open far past `MAX_REQUEST_SECONDS`. That is the same thread-pinning problem AUD-64 describes, moved into the header phase. All current fixtures send headers immediately, so no test catches it.
   - **Expected:** total wall time per request, headers included and across all redirect hops, ends at `req_deadline`. When it does, the call returns `None` or raises a timeout, and `requests_timed_out` goes up by exactly 1. One way: a per-request watchdog that shuts down the underlying socket at `req_deadline`, with the socket captured through an `HTTPAdapter` or connection hook.
   - **Checked next round by:** a new test with a raw-socket fixture that, after accepting, sends `HTTP/1.1 200 OK\r\nX-Pad: ` plus 300 bytes at 10 B/s, with `config.MAX_REQUEST_SECONDS=3` and `timeout=(3.0, 10.0)`. `client.get(...)` must finish in ≤ 4.5 s and `client.requests_timed_out == 1`.
2. [AUD-64] `core/http_client.py:599-631` (the `_pacing_send_lock` branch) and the removed `self.politeness.pace_request()` in `request()`: revert to the base behavior (`pace_request()` before the send, no lock around `session.send`).
   - **Why:** the default pacing is `DEFAULT_REQUEST_INTERVAL_MS = 50` (`core/politeness.py:20`), so this branch runs on every real scan. It holds one global lock through connect, sending the request and receiving the headers. One slow response then blocks every plugin thread, for example a time-based SQLi payload where the server sleeps before replying. The branch also writes the private `politeness._next_allowed_at` to measure from send completion, which changes pacing semantics. None of this is in the AUD-64 required fix, and the handoff lists "Deviations: none".
   - **Expected:** with `request_interval_ms > 0`, concurrent requests' sends are not serialized.
   - **Checked next round by:** `git diff 091fbbe -- core/http_client.py` shows no `_pacing_send_lock` and no `_next_allowed_at` writes. A test with `PolitenessEngine(request_interval_ms=50)` and 5 concurrent `get`s to a fixture that sleeps 2 s before sending headers finishes in under 4 s total.
3. [AUD-64] `core/http_client.py:19` (`import unittest.mock`) and `_consume_bounded_body:423-434` (the `isinstance(resp, unittest.mock.NonCallableMock)` early return): production code must not branch on test-double types.
   - **Why:** this branch lets existing MagicMock-based tests skip the new bounding logic entirely. That weakens those tests without changing them.
   - **Expected:** remove the import and the branch. Where an existing test genuinely breaks, give its mock a real `_content: bytes` (already handled by the `existing_content` branch at ~436) or a configured `iter_content`, and record that in the handoff.
   - **Checked next round by:** `grep -n "unittest" core/http_client.py` returns nothing, and the full suite still passes.

## Notes
- `requirements.txt` allows `urllib3>=2.0.0`, but the bounded `read1` path depends on `HTTPResponse.read1`, which I believe arrived in urllib3 2.1. On 2.0.x the code falls back to `iter_content(65536)`, which checks time only after a full chunk, so a dripping body is unbounded again. Consider requiring `urllib3>=2.1` or bounding the fallback.
- A response cut short by the time limit sets `truncated=True` but increments only `requests_timed_out`, not `responses_truncated`. If AUD-59 will report "responses truncated" as all truncated responses, decide that mapping explicitly there.
- I could not run probe scripts (shell execution was denied in this session). The verdicts above come from reading the diff and the tests, plus the precheck's passing suite. Required change 1 rests on how `requests`, `urllib3` and `http.client` apply socket timeouts, not on an observed run.
