## Required changes
1. [AUD-48] plugins/command_injection_plugin.py:run(): the control payload is `payload.replace(MARKER, "AUTOSEC_CTRL_TEST")`, which is `; echo AUTOSEC_CTRL_TEST`. The control still executes.
   - On a real shell-injection sink, the control response equals the test response with the marker swapped, so branch 1 (`response.text.replace(MARKER, ctrl) == ctrl_resp.text`) labels real RCE as "reflection" and suppresses it.
   - On the real testbed, the control to `/api/exec` returns `{"output":"Executed: ; echo AUTOSEC_CTRL_TEST"}`. That contains both `ctrl_marker` and `ctrl_payload`, so branch 2 fires and `/api/exec` is suppressed in the parameter path and in the JSON-body path.
   - The timing fallback also misses it: POST probes send no body.
   - The acceptance criterion "`/api/exec` is still reported" therefore fails on the real testbed. The unit test passes only because its mock's non-marker branch doesn't echo the input, which the real `/api/exec` does.
   - Expected: the execution probe must produce output that the input text cannot contain. Example: `; echo AUTOSEC_$((6*7))_RCE` is reported only if `AUTOSEC_42_RCE` is in the response, and the literal payload string alone never counts.
   - Expected: if a control is used, it must be inert. For example, the same characters quoted or escaped so a shell won't run them, or the expected-output token without any shell metacharacters.
   - Expected: drop the blanket `if payload in response.text: is_reflection = True` rule. Real sinks often echo the command back next to its output.
   - Checked next round by: a unit test whose fake server runs the command AND echoes the input (`f"ran {cmd}: " + output`) must yield exactly 1 finding; the existing echo-only test must still yield 0; plus the testbed test from item 4.
2. [AUD-49] plugins/sqli_plugin.py:_test_login_endpoints: findings are marked `verified: True` / confidence `high` without any baseline comparison, which breaks the project's false-positive rule.
   - `is_redirect_bypass` is true for any redirect whose `Location != login_path`. That includes absolute URLs and `/login?error=1`.
   - `has_cookie_bypass` is true for any 200 response that sets any cookie. Most frameworks do that on every response.
   - Expected: for each mode and field pair, also send a control login with a benign invalid username (for example `autosec_invalid_user`). Report only when the injected response shows a success signal (redirect to a different location, a new session cookie, or a 2xx where the control got 4xx) that the control response lacks.
   - Checked next round by: a unit test where the server always answers 302 to `/login?error=1` and sets a cookie on every response yields 0 login findings, while the existing form-encoded bypass test still yields ≥1.
3. [AUD-50] core/models.py:compute_canonical_key: the hard-coded overrides force a key of `secret_exposure` (if `.env` appears in the endpoint or title) or `auth` (if the endpoint is `/admin` or the title contains "admin panel"), and blank the param, whatever the real vuln_type is.
   - So an SQLi or XSS finding on `/admin?id=` or `/admin?q=` is merged into the "admin panel exposure" finding and lost.
   - Expected: canonicalize vuln_type through the taxonomy/alias table. Map plugin-specific types such as `dir_brute` and "misconfig + sensitive-file" to `secret_exposure` / `auth` via `normalize_vuln_type_key` or the alias data, never by endpoint or title substring.
   - Expected: a finding with a real injection vuln_type must keep its own key.
   - Checked next round by: a unit test where `merge_canonical([admin_panel_exposure, sqli_on_/admin?id])` returns 2 findings and the SQLi keeps `vuln_type="sqli"` and its param.
4. [AUD-48/49/50] All three acceptance criteria say "against the testbed" / "a real testbed scan", but every new test uses hand-written mocks. The AUD-48 mock even differs from the real `/api/exec` behavior.
